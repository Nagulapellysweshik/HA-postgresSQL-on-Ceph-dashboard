# T0, capacity sweep: debugging

## Blockers hit

### B1. The "ceiling" might have been the load generator
- **Symptom:** cap1 flattened at ~3 200 tx/s.
- **Diagnosis:**
  - Little's law: max tx/s ≤ connections ÷ latency = 64 ÷ 18.8 ms ≈ 3 400. That's exactly the plateau.
  - Reading the script showed `lib.sh` had already set `WORKERS=64`, so the intended `WORKERS=${WORKERS:-128}` never applied.
- **Fix:** `CAP_WORKERS` (default 128). Then cap2 tested the hypothesis: throughput **fell** with more connections, so the database was the limit.
- **Lesson:** before reporting a ceiling, check it isn't your client's.

### B2. ~1 450 errors per run in cap2
- **Diagnosis:** the summary showed only connect errors. The analyzer truncated the message, so the reason came from `grep -m1 -o 'FATAL.*' /logs/cap2-r3000/errors.log` → `too many clients already`.
- **Root cause:** 128 direct connections vs `max_connections 100`. About 33 were refused and retried once a second: 33 × 45 s ≈ 1 485.
- **Fix (tooling):** the analyzer now strips libpq's host/port prefix so the Postgres reason is visible.
